# 临床新能力接入规范指导

> 面向对象：接手接入工作的**人**，以及阅读本文件的 **AI 助手**。
> 目标：新增一个临床试验来源（渠道）时，**不改宿主编排逻辑、不改状态机、不改 UI 渲染**，只做声明式接入。
> 适用范围：`xyb.trials` + `xyb.trial-sources` 这一组「找试验」能力的渠道扩展。
>
> 相关文件：`docs/spec/xyb-unified-trial-host-orchestration.md`（宿主编排 SPEC，本文件的架构依据）、
> `docs/adr/0311-deterministic-channel-orchestration.md`（架构方向）、
> `XYB-TRIAL-UNIFIED-QUERY.md`（现行检索与合并契约）。

---

## 0. 一句话结论

**pi-desktop 已经有完整的插件接入框架**（manifest 声明式能力 + 权限矩阵 + 打包/市场），
新渠道不需要宿主发版，也不需要新的插件 SDK 能力。本文要做的只有一件事：

> 把「这个渠道是什么、怎么调、属于哪类数据、有什么副作用」写进一份**宿主侧来源描述符**，
> 然后按既有渠道的模式接上去。

既有五个渠道（ClinicalTrials.gov / ChiCTR / Veeva CTV / 中国药物临床试验登记平台 / WHO ICTRP）就是五份参考实现。
其中四种接入形态都已跑通，你只需要挑一种照着做。

> **第五种形态（2026-10-04 新增）：随包 vendoring 一个 Python MCP 服务。** WHO ICTRP 走的是这条路——
> 源码随插件分发、由 `python3 -m` 启动、依赖由用户在环境里安装。它和形态 B 的区别在于**分发方式**
> （源码进包，而非依赖 npm/PyPI 拉取）与**运行时风险**（Python 不在本项目控制范围内，必须做四级探测与
> 可复制的修复指引）。详见 `docs/spec/xyb-unified-trial-host-orchestration.md` §15.3。

## 1. 先选接入形态

新渠道属于哪一种？对照下表确定，不要混用。

| 形态 | 适用场景 | 既有参考 | 需要什么权限 |
|---|---|---|---|
| **A. 宿主直连 HTTP** | 有稳定公开 JSON API，无本地进程、无登录 | ClinicalTrials.gov（`xyb.trials`） | `net.fetch` + manifest 出网白名单 |
| **B. 声明 MCP 服务器** | 已有 MCP 服务，或需要独立进程（浏览器、Python、本地库） | ChiCTR、Veeva CTV（npm 包）、中国药物临床试验登记平台（插件自带脚本） | `mcp.server.local` |
| **C. 插件自注册工具** | 纯 JS 逻辑，不需要独立进程 | `xyb.trials` 的 `xyb_trials_search` | `agent.tool.register` |
| **D. 随包 vendoring MCP 服务** | 上游只有源码、不在 npm/PyPI 上，且希望开箱即用 | WHO ICTRP（`xyb.trial-sources` 自带 `mcp/ictrp/`，`python3 -m ictrp_mcp.server`） | `mcp.server.local` |

**默认建议选 B。** 理由：权限表里**不存在「执行外部进程」这一项**，本地工具的唯一正规通道就是
`contributes.mcpServers`；而且 B 天然把重依赖（Python、Playwright、本地数据库）隔离在插件自己的进程里，
主应用不必为某个数据源背依赖。

**形态 D 的额外代价（选它之前先读）**：源码随包分发意味着你**不能**假定运行时存在。WHO ICTRP 因此要求
四级探测（可执行文件 → 随包模块 → 第三方依赖 → MCP 握手），失败时报 `NEEDS_SETUP` 并给出**可复制**的
修复命令，**绝不**渲染成「未查到」。还要注意三个宿主限制：`env.PYTHONPATH` 以插件根目录为基准、
宿主不自动定位 `python3`（`NODE_LAUNCHERS` 只覆盖 node/npx/npm）、调用超时必须显式传
`callTimeoutMs`（默认 100s 会超过 60s 来源期限）。详见 SPEC §15.3.6.1。

**形态 D 的完整落地步骤见 §3.5**（含 vendoring 目录树、门禁脚本、以及两次真实漂移的处置）。

**禁止的形态**：插件之间互相调用 MCP 工具。插件 SDK **没有**跨插件 MCP 调用 API，这是刻意的
（见 SPEC §4.1）。渠道只能暴露成宿方可发现的**工具**，由宿主编排器去调用。

## 2. 形态 A：宿主直连 HTTP

### 2.1 前置条件

- 接口是公开、稳定的 JSON API（不要接需要登录的）；若是 HTML 页面需要 JS 渲染才能出结果，**不适合本形态**。
- 在 manifest 里声明 `net.fetch` 权限，并把域名加入出网白名单。
- 必须能提供**规范化登记号**（NCT / CTR / ChiCTR / UTN 等），否则不具备合并资格（见 §5）。

### 2.2 manifest 写法

```jsonc
{
  "permissions": ["ui.view", "agent.tool.register", "agent.prompt.inject", "net.fetch"],
  "contributes": {
    "agentTools": [
      {
        "name": "xyb_trials_search",
        "description": "……（写清楚：这是哪个来源、返回什么、边界在哪）",
        "risk": "low",
        "schema": { "type": "object", "properties": { "condition": { "type": "string" }, "terms": { "type": "string" } } }
      }
    ]
  }
}
```

出网白名单见 `docs/spec/07-plugins/02-plugin-manifest-schema.md:398-427`；确需任何域名时走 `net.anyHost` 逃生口，
但要在评审里单独说明理由。

### 2.3 ⚠️ 宿主 `pi.net.fetch` 的返回形态（最容易踩的坑）

**返回值是普通对象 `{ status, headers, bodyText }`，不是 Web `Response`。**

- **没有** `.ok`
- **没有** `.json()`

2026-10-03 就是因为写成 `if (!res.ok)`（恒为 `undefined` → 恒真），导致 CT.gov 与 PubMed 在应用内
**100% 失败**，还被误归类成网络错误。正确写法：

```js
const res = await pi.net.fetch({ url, method: "GET", headers: { accept: "application/json" }, timeoutMs: 20000 });
const ok = res && typeof res.status === "number" && res.status >= 200 && res.status < 300;
if (!ok) {
  // 区分状态：429 → RATE_LIMITED，5xx → UPSTREAM_ERROR，其余 → 按状态码如实报
  return { ok: false, reason: res?.status === 429 ? "RATE_LIMITED" : "UPSTREAM_ERROR", status: res?.status };
}
const data = JSON.parse(res.bodyText);   // 优先解析 bodyText
```

另外注意**签名只接受一个对象参数**：`pi.net.fetch({ url, method })`。
写成 `pi.net.fetch(url, { method })` 会让 `input.url` 是 `undefined`，宿主抛 `only http(s) URLs allowed`。

### 2.4 单元测试要求

必须有一条测试**用真实的宿主返回形态**（`{status, headers, bodyText}`）跑通解析路径，
并覆盖：429、5xx、无响应、JSON 非法。既有参考：`apps/desktop/test/xyb-trials-errors.test.mjs`。

## 3. 形态 B：声明 MCP 服务器（推荐）

### 3.1 四种子类型

| 子类型 | 例子 | manifest 写法 |
|---|---|---|
| 公开 npm 包 | ChiCTR `chictr-mcp-server@3.0.2`、Veeva `ctv-mcp-server@0.1.0` | `"command": "npx", "args": ["-y", "<包>@<精确版本>"]`（可另加 `"env"`，如 ChiCTR 的 `"CHICTR_USE_SIDECAR": "1"`） |
| 插件自带脚本 | 中国药物临床试验登记平台 | `"command": "./mcp/<name>-mcp.mjs"` |
| 随包 vendoring 的 Python 服务 | WHO ICTRP | `"command": "python3", "args": ["-m", "ictrp_mcp.server"], "env": { "PYTHONPATH": "./mcp/ictrp" }` |
| 远程 HTTP | （暂无参考） | `"transport": "http"`, `"url": "https://..."`（还需 `mcp.server.remote` 权限） |

**npm 包必须锁精确版本。** 不要写 `@latest`。既有教训：本机全局装过旧版 `chictr-mcp-server`，
其 `search_trials` 参数是 `keyword` + `months`，与 `@2.0.2` 的 `registration_number` / `year`
**不兼容**，所以插件固定用 `npx ...@2.0.2`，不能用全局命令。

### 3.2 manifest 写法

```jsonc
{
  "permissions": ["ui.view", "agent.prompt.inject", "mcp.server.local"],
  "contributes": {
    "skills": ["skills/<your-source>.md"],
    "mcpServers": [
      {
        "id": "a-channel",                       // 宿主工具名前缀就用它
        "label": "A 渠道（一句话说明覆盖范围）",
        "transport": "stdio",
        "command": "npx",
        "args": ["-y", "a-channel-mcp-server@1.2.3"]
      }
    ]
  },
  "settings": [
    { "key": "aChannelDataDir", "type": "string", "title": "A 渠道数据目录",
      "description": "留空使用默认位置……", "default": "" }
  ]
}
```

配置注入用 `{"setting": "<key>"}`，宿主会从**该插件自己的 settings** 取值（不会跨插件）：
`"env": { "A_CHANNEL_DATA_DIR": { "setting": "aChannelDataDir" } }`。

### 3.3 自带 MCP 服务的实现约定

参考 `apps/desktop/resources/plugins/xyb.trial-sources/mcp/chinadrugtrials-mcp.mjs`：

1. **零 npm 依赖**，只用 Node 内置模块。患者机器不该为了一个数据源再装一堆包。
2. **stdio 传输**，行分隔 JSON-RPC 2.0（同时兼容 `Content-Length` 帧，防宿主用旧式分帧）。
3. **工具要少而稳**，命名用动词+名词：`search_*` / `get_*_detail` / `list_archived` / `verify_archive` /
   `get_collector_status`（排障入口）。
4. **排障工具与检索工具分开**。`setup_environment`、`update_cookie`、`clear_cache` 这类
   **有副作用或需要用户本人操作的工具，绝不能混进检索路径**。
5. **凭证红线**：Cookie / token 只写本机数据目录（权限 `0600`），
   **不写日志、不写返回值、不进提交**；传给子进程走 `--config` 文件而不是命令行参数
   （命令行会出现在进程列表里，会被别的进程读到）。

### 3.4 最小工具集（新渠道应当具备）

| 工具 | 作用 | 必需 |
|---|---|---|
| `search_*` | 检索，返回带登记号的记录 | ✅ |
| `get_*_detail` | 按登记号取详情 | ✅ |
| `get_*_status` | 前置条件自检（依赖 / 会话 / 索引就绪） | ✅ 强烈建议 |
| `list_*` | 看本机已归档/索引了什么 | 可选 |
| `verify_*` | 归档/索引完整性核对 | 可选 |

### 3.5 形态 D：随包 vendoring 一个 Python MCP 服务

既有参考：WHO ICTRP。插件目录 `apps/desktop/resources/plugins/xyb.trial-sources/`，
随包源码在 `mcp/ictrp/ictrp_mcp/`，manifest 里以 `"command": "python3", "args": ["-m", "ictrp_mcp.server"]`、
`"env": { "PYTHONPATH": "./mcp/ictrp" }` 启动。

#### 3.5.1 为什么要有这一节

形态 B / D 在 manifest 上只差一行 `command`，但**维护责任完全不同**：形态 B 的代码在 npm 上，
上游发新版不会影响你；形态 D 的代码**是仓库里的副本**。副本一旦落后上游，不会报错——
只会在运行时以「某个工具神秘消失」或「某个字段恒为空」的形式暴露，而那是用户已经在用的功能。
所以形态 D 必须配一条**构建期**门禁，把沉默的运行期故障前移成响亮的构建失败。

#### 3.5.2 vendoring 目录树约定

```
xyb.trial-sources/
├─ manifest.json                       # contributes.mcpServers 指向下面目录
├─ mcp/
│  ├─ ictrp/                           # ← vendoring 根的父目录（PYTHONPATH 指向它）
│  │  └─ ictrp_mcp/                    # ← 上游包的顶层模块名必须原样保留
│  │     ├─ __init__.py
│  │     ├─ server.py                  # 工具注册在这里
│  │     ├─ tools.py
│  │     ├─ data/
│  │     ├─ ictrp/
│  │     └─ cache/
│  └─ chinadrugtrials-mcp.mjs          # 形态 B 的自带脚本，与 Python 树并列
└─ ATTRIBUTION.md + LICENSE-<upstream>
```

硬性要求：

- **上游模块名原样保留**（`ictrp_mcp/` 不能改名）。`python3 -m ictrp_mcp.server` 是按模块名导入的，
  改名会让 `PYTHONPATH` 静默失效。
- **只放运行所需文件**：排除 `__pycache__/`、`*.pyc`、`tests/`、`fixtures/`、`docs/`、`.venv/`。
  留档一份 42MB 的测试夹具没有任何好处。
- **随包树必须与上游逐字节一致**，不做本地修改。要改就先改上游、再重新同步。
  就地改随包副本的后果是：下次同步时你的修复会被静默抹掉，且无人知道曾经有过这个修复。
- **`ATTRIBUTION.md` 与上游许可证一同随包**。WHO ICTRP 还额外要求归因与「处理日期」随数据可见
  （见 §5.3 与 SPEC §15.7）。

#### 3.5.3 门禁脚本（形态 D 的必做项）

既有实现：`scripts/xyb-check-ictrp-vendor.mjs`，已接入 `package.json`：
`"check:ictrp-vendor": "node scripts/xyb-check-ictrp-vendor.mjs"`。

它校验三件事，缺一不可：

1. **必需模块清单齐全**。少一个模块，MCP 服务器就起不来，而 IDE 里看不出来。
   新渠道要自己维护这份清单（以 `server.py` 里实际 `import` 到的模块为准，不是凭印象写）。
2. **无 `__pycache__` / `*.pyc` / `*.pyo`**。`.pyc` 可能嵌入本机构建的绝对路径，
   是「在我机器上能跑」的经典来源。注意 `.gitignore` 忽略它们**不等于**它们不存在——
   跑一次 Python 就会再生成，这正是门禁要拦的原因。
3. **可选逐字节比对**：`--upstream <repo>` 或环境变量 `ICTRP_UPSTREAM`。
   指向规范副本（npm 包里的 sidecar vendor 目录通常比源码仓库更适合做基线，因为它带版本戳）。

**漂移必须用 `fail`（exit 1），不能用 `warn`。** 差异只有两种可能：要么有人就地改了随包副本
（下次同步会丢），要么上游变了而本仓库没跟上（需要人裁决）。两者都需要人处理，
用警告会被静默滑过去。反向自证一次：临时往某个 `.py` 追加一行注释 → 门禁应 `exit=1`；
还原 → `exit=0`。**一条永远不失败的门禁与没有门禁是同一件事。**

#### 3.5.4 两次真实漂移（照着这个流程处置）

| 轮次 | 漂移文件 | 上游变化 | 处置 |
|---|---|---|---|
| 第一次 | `ictrp/session.py` | 新增 `DEFAULT_TIMEOUT_SECONDS=120.0`、`ICTRP_TIMEOUT`、`DEFAULT_ATTEMPTS=3`、`ICTRP_ATTEMPTS`、`RETRYABLE_CODES` 与 `retry()` 包装 | 从规范副本 `cp` 覆盖 |
| 第二次 | `data/normalize.py`、`tools.py` | 新增 `line_of_therapy_hint` 派生字段、扩充 `DEFAULT_FIELDS` | 从规范副本 `cp` 覆盖 |

处置流程是固定的四步：**① 门禁报差异 → ② 读上游 diff 判断是修复还是重构 → ③ 从规范副本覆盖
→ ④ 重跑门禁至全绿**。第 ② 步不能省，因为上游也可能引入回归。

**第一次漂移里的一个设计判断值得记住**：`RETRYABLE_CODES` **刻意排除**了 `UPSTREAM_BLOCKED`。
重试一个正在拒绝你的端点只会加重封禁，并掩盖「我被封了」这个真正需要告诉用户的诊断。

#### 3.5.5 ⚠️ 派生字段与喂给它的原始列必须同进同出

这是第二次漂移里最有价值的教训，比漂移本身重要：

上游新增了 `line_of_therapy_hint`，由 `inclusion_criteria` / `exclusion_criteria` 两段自由文本派生。
而随包种子为了控制体积，用 `ICTRP_KEEP_FIELDS` 白名单裁字段——**裁掉的正是那两段自由文本**
（原稿合计 14.91MB）。同时，**离线路径 `cache/store.py` 的 `adopt()` 原样采纳快照里的 trials，
不走 `to_trial()` 归一化**（只有实时路径才走）。结果是：

> 离线查询 `fields=["line_of_therapy_hint"]` 返回 **`None`**，100 条全 `None`。

上游 docstring 写得很清楚：`None` 意为 *"not stated in the criteria we hold"*，
**不得读作 first-line**。但一个名为 `line_of_therapy_hint` 的字段整齐地全空，
极易被模型读成「都是一线 / 未经治疗」——**从数据缺失直接推出临床结论，且方向恰好是错的**。

处置办法（新渠道遇到同类问题照做）：

1. 在种子文件的 `snapshot.field_note` 里**明写**哪些列未随包、哪些字段因此恒为 null、
   **不得反推**什么结论；
2. 让生成脚本也写这段说明，重跑不会擦掉；
3. 加一条测试把「说明必须存在」与「数据里确实一条都没带该字段」**钉在一起**。

教训原话：**「字段存在但恒为空」比「字段不存在」更危险，因为空值看起来像一个答案。**

#### 3.5.6 形态 D 的检查清单

- [ ] 随包树与上游逐字节一致，模块名原样保留
- [ ] 无 `__pycache__` / `*.pyc` / `tests/` / `fixtures/` / `docs/` / `.venv/`
- [ ] `check:<source>-vendor` 门禁已建并接入 `package.json`，漂移用 `fail` 不用 `warn`
- [ ] 门禁做过反向自证（注入一行改动应报错）
- [ ] `ATTRIBUTION.md` + 上游许可证随包
- [ ] 四级探测（可执行文件 → 随包模块 → 第三方依赖 → MCP 握手）齐全，失败报 `NEEDS_SETUP`
- [ ] 加了派生字段 → **确认派生所需的原始列也在随包里**，否则必须在 `field_note` 里声明并加测试
- [ ] 运行期前置（Python 版本、第三方包、Playwright 浏览器等）写进技能文档，附**可复制**的修复命令

## 4. 形态 C：插件自注册工具

适用于纯 JS、无独立进程的渠道。参考 `xyb.trials`。

- 权限：`agent.tool.register`
- **必须声明 `risk`**，且不得低于 `medium`（外部数据取数属 medium，见下）
- 必须提供 `schema`，参数名要能映射到宿主统一形状（见 §5.2）

注意：**插件工具是按需激活的**。宿主为省上下文，插件工具默认不进工具列表；模型直接调用会得到
`Tool plugin_... not found`——这不是插件坏了。技能文档里必须写明「先 `ToolSearch` 查询激活，下一轮才能调用」，
这是既有渠道都踩过的用户可见故障。

## 5. 既有渠道已验证的临床细化原则

这些是**临床主题特有的**约束，不能指望通用插件框架替你保证。新渠道一律适用。

### 5.1 登记号优先

能提供规范化登记号（`NCT` / `CTR` / `ChiCTR` / `UTN` 等）的记录才具备**合并资格**；
无登记号的记录保持独立、不参与去重。**标题或药物相似不构成合并理由。**

实测回归用例：Veeva 返回的 `NCT07066098`、`NCT07483554` 与 CT.gov 结果重复，合并后**不得重复计数**。

### 5.2 参数映射由描述符负责，不交给模型猜

各渠道的参数名**不一致**，这是实测踩到的坑：

| 渠道 | 实际参数 |
|---|---|
| CT.gov | `{ condition, terms }` |
| Veeva CTV | `{ condition, terms }` |
| ChiCTR | `{ keyword, max_results }` |
| 中国药物临床试验登记平台 | `{ keywords, max_pages, ... }` |
| WHO ICTRP | `{ keyword, limit, offset, ... }`（**无** `condition` 参数，仅按 `terms` 检索） |

新渠道自己的参数名写进描述符的 `argShape`，由宿主做映射。**不要让模型在不同参数名之间做选择**，
它会选错。

### 5.3 诚实标注证据等级

新渠道必须声明自己属于哪一类，并在界面上如实呈现：

| `kind` | 含义 | 呈现要求 |
|---|---|---|
| `remote_registry` | 实时远端注册库 | 可以说「实时检索」 |
| `local_index` | 本地索引 / 快照 | **必须暴露构建或刷新时间**，不得表现为实时全球检索 |
| `archived_scrape` | 抓取归档 | 必须走副作用同意闸门；引用时给登记号 + 原文链接 |
| `aggregator_registry` | 聚合注册库（收录多个一手注册库） | **不得**表现为一手来源；与一手来源命中同一登记号时保留一手版本并标注「via <聚合库>」；条数语义通常是**下界** |

Veeva 就是 `local_index`，且还有已知缺口：全文检索表 `studies_fts` **漏收了经 graphql 途径入库的记录**
（库里明明有 `YL201` 8 条，`search_studies {keyword:"YL201"}` 却 0 命中）。因此 **0 命中永远不能说成
「没有相关研究」**，只能说「本地索引中未命中」并附覆盖说明。

### 5.4 不做列表页抓取

**JavaScript 渲染的检索/列表页不构成注册库证据。** 2026-10-03 助手绕过渠道工具、直接抓
`clinicaltrials.gov/search`、`chinadrugtrials.org.cn/search.html`、`chictr.org.cn/search` 三个检索页，
**全部失败**。

允许的浏览器补充只有一种：**已知具体登记号后打开该条记录的详情页**，且来源要单独标注。
这条规则对新渠道同样生效，**没有「新来源特例」**。

### 5.5 副作用必须前置披露

任何抓取、写盘、登录、安装依赖都**必须进入同意闸门**，不允许静默发生：

> **2026-10-04 修订（覆盖本条此前对 CDE 的表述）：** 中国药物临床试验登记平台**不再**因写盘而被排除在静默扇出之外。
> 用户否决了原「副作用同意闸门」设计，理由有两条：写本地归档不是破坏性操作；每次查询都弹同意会重新制造
> 「用户被迫手打工具名」的失败模式。**当前规则是：CDE 与其余来源同等纳入扇出，读的是本机归档，无副作用。**
> 只有**联网取数**（`search_trials` / `sync_incremental`，会写盘与抓站）留在扇出之外，按 §7.5 的更新路径处理。
> 依据：`docs/spec/xyb-unified-trial-host-orchestration.md` §4.3；ADR 0311 §4 的取代说明。

- 中国药物临床试验登记平台的**联网取数**（`search_trials` / `sync_incremental`）会把详情页原始 HTML、
  结构化 JSON、平台原样 Word **归档到本机**，因此**不在查询扇出内**；查询扇出只读本机已有归档。
- `setup_environment`、`update_cookie`、`refresh_cookie` **永不隐式调用**。
- **规则**：`sideEffect: "local_archive"` 不进**静默**扇出，**无论它是第几个渠道**；`local_cache`
  （如 WHO ICTRP 的缓存写入）允许留在扇出内，但必须可审计、写入用户数据区、且写失败不得导致来源失败。

### 5.6 失败状态必须可区分（这是最重要的一条）

终态定义（完整版见 SPEC §5.2）：

| 状态 | 含义 | 常见误用 |
|---|---|---|
| `SUCCESS` | 成功且 ≥1 条记录 | — |
| `NO_RESULTS` | **查过**，明确 0 条 | 被拿去顶替下面所有状态 ❌ |
| `NOT_ENABLED` | 被设置**明确**关闭（**唯一**合法用法） | 把「工具没注册」写成它 ❌ |
| `NEEDS_SETUP` | 已启用但缺前置（依赖/索引/会话），**含工具未注册但根因是前置缺失** | 渲染成「未查到」 ❌ |
| `NOT_QUERIED` | 未派发，须带原因 | — |
| `TIMEOUT` | 已派发但超期 | — |
| `CHALLENGE_REQUIRED` | 需要人工验证；永不绕过 | — |
| `FAILED` | 传输/协议/上游/结构失败 | — |

**只有 `SUCCESS` 与 `NO_RESULTS` 算「查过」。**

### 5.7 条数必须自报截断

每个 `SUCCESS` 结论都带 `truncated: boolean` 与请求/返回条数，使受分页上限影响的结果
**不会被当成总数**呈现。CT.gov、ChiCTR、Veeva、CDE 都接受调用方上限。

### 5.8 新鲜度可见

能报告数据的时点或构建时点；不能的话，界面必须明示「新鲜度未知」。

### 5.9 风险等级不得低于 medium

MCP 与外部网络抓取在既有权限判定下都属于 `medium`：
`ask` 模式需审批，`auto` 可自动放行，`accept-edits` **不会**自动放行 medium。
沿用既有语义，**不要为了少弹窗而把风险标成 low**。

## 6. 登记来源描述符（宿主侧，唯一需要在宿主改动的地方）

在宿主的封闭来源注册表里增补一条记录（SPEC §6.2）：

```ts
type TrialSourceDescriptor = {
  key: "clinicaltrials_gov" | "chictr" | "veeva_ctv" | "chinadrugtrials" | "who_ictrp" | "<new_key>";
  pluginId: string;             // 例如 "xyb.trial-sources"
  toolName: string;             // 已注册工具 ID，必须是评审过的固定值
  argShape: "condition_terms" | "keyword_maxresults" | "keyword_limit_offset" | ...;
  kind: "remote_registry" | "local_index" | "archived_scrape" | "aggregator_registry" | ...;
  sideEffect: "none" | "local_archive" | "local_cache" | ...;
  defaultLimit: number;
  timeoutMs: number;
  freshness: "live" | "build_time";
};
```

**硬性规定：描述符由宿主持有，插件不能自行注册。**
让插件声明「我是合格试验来源」等于让插件自我授权进入扇出，会重新引入 SPEC §4.2 明确禁止的推定同意。
若将来要开放插件自注册，必须另立 ADR 并单独评审。

## 8. 反面案例（真实踩过的坑，务必读完）

1. **`pi.net.fetch` 返回形态误用** → CT.gov / PubMed 在应用内 100% 失败，
   且被误归类为网络错误。修复提交 `32c5ce7af`。
2. **漏渠道不报错**：用户问「按渠道汇总 IBI343 数量」，助手加载技能后只查了 CT.gov 与 ChiCTR，
   Veeva 与中国药物临床试验登记平台**从未被查询**，`xyb_trials_unify` 从未调用，**且不报错**。
   用户拿到看起来像多渠道汇总、实际只有两个渠道的答案。
3. **误标 `NOT_ENABLED`**：中国药物临床试验登记平台当时是**启用且可用**的，
   真实原因是「工具不在当前上下文」，却被写成 `NOT_ENABLED — 本工具未在当前上下文就绪；本次未查到`。
   这个误导性标签**直接导致用户没拿到本可拿到的正确结果**——他后来手动打 `search_trials`
   才拿到 5 条 CTR 记录。
4. **让用户手打工具名**：composite 卡住后，用户不得不自己补上缺失的工具名。
   这属于产品失败，不是用户操作问题。
5. **绕过渠道工具抓检索页**：三个 JS 渲染的检索页全部失败，浪费一整轮。
6. **参数名不统一**：不同渠道 `condition/terms` 与 `keyword/max_results` 混用，
   交给模型选择必错。
7. **技能加载成功 ≠ 完整扇出**：技能正确加载、工具正确激活，但编排仍然漏渠道。
   所以完整性必须是**宿主操作的属性**，不能指望助手自觉。
8. **随包 vendoring 的上游漂移是静默的**：随包 Python 树落后上游两个版本时，没有任何报错，
   只在运行时表现为「某个工具少了参数」「某个字段恒为 null」。必须用 §3.5.3 的构建期门禁拦截，
   且漂移判定必须 `fail` 而不是 `warn`。
9. **字段存在但恒为空**：`line_of_therapy_hint` 在离线路径整齐返回 `None`，
   因为随包种子裁掉了它依赖的自由文本列。空值看起来像一个答案，
   模型会把它读成「都是一线」——**从数据缺失推出临床结论，方向恰好相反**。
   派生字段与喂给它的原始列必须同进同出（§3.5.5）。

## 9. 给 AI 助手的使用说明（可直接粘贴给 AI）

> 你要接入一个临床试验新渠道。请先阅读仓库中的
> `docs/guide/临床新能力接入规范指导.md`（本文件）与
> `docs/spec/xyb-unified-trial-host-orchestration.md`，然后：
>
> 1. 判断该渠道属于形态 A（宿主直连 HTTP）、B（声明 MCP 服务器，推荐）、C（插件自注册工具）
>    还是 D（随包 vendoring MCP 服务），并说明理由。
> 2. 按第 3 章（B / D）或第 2 章（A）落地 manifest 与代码，**npm 包锁精确版本**。
> 3. 按第 5 章九条临床细化原则逐条自查，特别是：
>    登记号优先、参数映射不交给模型、诚实标注证据等级、不做列表页抓取、
>    副作用前置披露、失败状态可区分、条数自报截断。
> 4. 按第 6 章在宿主描述符表增补一条记录（不得让插件自注册来源）。
> 5. 按第 7 章清单补测试与验收，并跑第 7.3 节的全部门禁。
> 6. **不要修改宿主编排器逻辑、状态机或 UI 渲染。** 如果你发现必须改，
>    说明描述符抽象不成立或该渠道不适合接入，**停下来报告，不要自行扩权**。
> 7. 不要提交、不要推送、不要合并；未经显式授权不得安装依赖。
> 8. 遇到无法满足的前置条件（需要登录、需要付费、需要人工验证），
>    **如实标注为 `NEEDS_SETUP` 或 `CHALLENGE_REQUIRED`，不得绕过**。
