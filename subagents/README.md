# MDT 视角子智能体（PI-Desktop）

一组**多学科视角**的子智能体定义：外科、肿瘤内科、影像、病理、介入、放疗、营养、心理、安宁疗护。
每个从自己专科的角度，帮患者与家属把「该弄清什么、该问什么」整理出来。

## 为什么这些东西不随插件自动生效

PI-Desktop 的插件**无法贡献子智能体**——插件清单里没有这个贡献点。这是刻意的设计，
源码注释写得很明白：

> Project workspaces never provide subagents; a repository cannot silently add a delegate
> to a user's agent catalog.

因为子智能体是**能行动的委派者**（内置的 `fixer` 手里有 Write 和 Bash）。
如果插件能贡献，装一个插件就等于静默获得了能力。所以子智能体被定为**用户级资产**，
只有两个来源：宿主随附的内置定义，和用户自己放进 `~/.agents/subagents/` 的 Markdown。

本目录是**定义源**（进版本库、可评审、可回滚）；装到本机要跑一次安装脚本：

```bash
bash scripts/xyb-install-subagents.sh              # 安装
bash scripts/xyb-install-subagents.sh --uninstall   # 卸载（只删本套装，不动别的）
```

装完需要**新开一个会话**（或重启应用）才会被加载。

## 定位：这是「视角」，不是「会诊意见」

这件事必须说在最前面。

真实的 MDT 是**多位医生一起看原片、看切片、看检验，共同署名负责**。
这里的九个是软件角色，没有看原片、没有看病理切片，也不承担任何责任。
把它包装成「五位专家会诊意见」，对癌症患者是危险的——会给出虚假的权威感。

所以整套设计的产出是：

- **该专科还需要哪些资料**（缺什么）
- **该专科判断时看什么维度**（依据）
- **可以拿去问该专科医生的具体问题 3–5 条**（真正有用的东西）
- **依据与不确定性**（哪些是共识、哪些有争议、哪些数据缺失）

**不是**：诊断结论、治疗方案、用药建议、能不能手术、预后多久。

输出里统一用「**XX 视角**」，不用「XX 专家」。汇总时必须呈现**各视角的分歧点**，
而不是把七份意见平均成一个结论——分歧恰恰是患者最该拿去问医生的东西。

## 为什么用子智能体而不是技能

MDT 的价值在于**意见互相独立**。如果让一个 Agent 在同一个上下文里依次扮演九个专科，
后写的会被前面的判断锚定，那样得到的不是多学科视角，而是一个观点的七种复述。

子智能体的上下文是隔离的，所以七份意见确实是各自独立得出的。附带好处：

- 可以**并行**发出去
- 每个专科只拿到**自己相关的那部分资料切片**，无关信息不干扰，也减少了不必要的暴露面
- 不需要读文件的专科，工具就只给 `Read`

## 技术规格（与源码校验规则对齐）

| 项 | 值 | 依据 |
|---|---|---|
| `name` | 小写字母/数字/连字符，≤40 字符 | `NAME_RE = /^[a-z0-9][a-z0-9-]{0,39}$/` |
| `description` | 必填，助手靠它决定是否委派 | `parseSubagentDefinition` |
| `tools` | 只能从 `Read / Glob / Grep / BrowserPreview / Bash / Edit / Write` 里选；**省略则默认 `[Read, Glob, Grep]`** | `SUBAGENT_ASSIGNABLE_TOOLS` / `DEFAULT_SUBAGENT_TOOLS` |
| 本套给的工具 | 一律 `[Read]` | 医学意见不需要写文件、不需要跑命令 |
| `model` | 不固定 | 缺省跟随会话模型；固定了但 provider 不存在会**报错而不是回退** |
| `thinkinglevel` | 不声明 | 档位与模型相关，声明了不支持的值只会被忽略 |
| 总数上限 | **16 个**（内置占 5 个） | `MAX_SUBAGENT_DEFINITIONS` |
| 并行上限 | 10 | `MAX_SUBAGENT_CONCURRENCY` |

**没有 shell 权限也没有写权限**：即便以后有人改了定义，只要工具集里没有 Bash/Write/Edit，
这个委派者就不可能动文件或执行命令。

## 名字显示

用户级子智能体在设置页显示的是 `name`（即 `mdt-pathology` 这样的 handle，因为
`id == name` 且必须是 ASCII）。这是 schema 约束，改不了。患者版里这一页本身
就建议不暴露，所以影响有限。

## 怎么用

在会话里说「帮我把这个病例从不同科室的角度理一遍，我该问医生什么」，
助手会按 `xyb.assistants` 插件里的「MDT 视角会诊准备」技能来编排：
先齐料、缺料就问、按需并行派发、最后汇总成一张问医生的清单。

## 与内置子智能体的关系

内置的 5 个（探索者 / 代码审查员 / 测试执行者 / 修复者 / UI 设计师）全是软件工程角色，
与患者无关，**已默认关闭**：

```bash
node scripts/xyb-disable-engineering-subagents.mjs            # 关闭（已执行）
node scripts/xyb-disable-engineering-subagents.mjs --enable   # 恢复
```

**为什么用脚本写状态文件而不是改代码**：host-core 的启用语义是
「全局级显式启用 = **删除记录**」（`agent_capabilities.rs:130-136`），
所以状态文件无法表达「我主动打开过」。若在代码里并上一个恒定禁用集，
用户手动打开后记录被删、恒定集仍然生效，**开关就变成了假的**。
写入 `false` 才能同时做到「默认关闭」与「可再手动打开」。

关闭后：**可委派目录**里不再有这 5 个（实测 14 → 9），
但**设置页仍保留 5 行**、可逐个手动打开。

本套 9 个 + 内置 5 个 = 14 个，未超过 16 的上限。

> 打包给患者时，这一步应该挪到**首次运行**里去（当前仓还没有 first-run 钩子），
> 否则新装机器上这 5 个仍是默认开。
